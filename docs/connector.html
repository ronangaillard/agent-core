The Connector contract

Two connectors in agent-core: Slack (live) and email (written, not yet enabled on the NAS). What they provide to the core: the core never reads an Address or a raw payload and never calls an external API. GitHub and the scheduler are not connectors but sources (below).

The sources (not connectors)
They build an InboxRow author_kind system whose address is a real connector's: the per-thread lock, read() and delivery work with no special case. Only the source_id carries their origin.
schedulerdue reminder → address = reminders.address; source_id reminder:id:due_at
GitHubfinal deployment_status → a configured address; source_id github:deploy:<deployment id>, the same via the signed webhook and the startup pass
tasksdo not go through the inbox: their reports are outbox reports to tasks.address
The core never
• reads a raw payload; of an Address, it only strips the ts (threadOf)
• calls Slack, Resend or GitHub
• knows the owner's commands: it is given a list (owner.ts)
• guesses a thread: it takes thread_key
The connector never
• decides permissions (scopeOf, in the core)
• writes to inbox or outbox itself
• replies on its own
• decides a retry: it says transient or not, the core decides
The owner's path
Their DMs with colleagues are never read (toInbox returns null: the bot is not a member). Their commands (held, send <n>, send <n>: text, drop <n>, help) are recognized by code on row.text in their DM with the bot, before anything else (outcome intercepted, no model); never by email. When a human mentions them where Steve would not speak, Steve writes the reply in their place: a held draft (outcome to_owner), with no side-effect tool, announced in their DM; send <n> posts it with their token. Polls have no code: send to people.
