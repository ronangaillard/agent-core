Tools and scopes: who may do what
The model chooses which tool to call and with which arguments. The code decides which ones exist for it, what they know about the conversation (the scope), and rechecks before executing. The tools are an in-process MCP server, built for each respond(); the tools of a remote MCP server (Notion) are wrapped into it, under the same rules.

What we don't do

• No plugin framework: a list of ToolDef (name, input zod, rules, effect, run) passed to the core, bound by bind().
• No MCP server of our own per domain: a separate process does not see the scope, it would have to be passed via env or hooks, with processes to manage. A third party's hosted MCP (Notion) is taken as it is: its tools become ToolDefs.
• No tool per need: generic capabilities (memory and shelves, send, files, reminders, tasks), never a business-specific tool.

Done in agent-core: the context carries the address, Slack writing goes through send(to, text), and tools with effects write an acted event.
